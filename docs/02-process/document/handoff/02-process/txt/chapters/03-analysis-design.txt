第 3 章 系统分析与设计

3.1 功能需求

系统的主要功能需求根据使用主体可以细化为管理后台、微信小程序以及微服务间协作三大部分

[工程图占位符: U05-系统用例图]
，各部分的业务规则和操作流程在设计之初便被严格定义，以确保系统在功能边界上不存在歧义。

对于管理后台而言，系统需要提供完备的安全鉴权管理，支持基于 JWT 令牌的用户登录、安全拦截、防重提交，以及基于 RBAC 体系的动态菜单加载和角色权限过滤。在角色权限分配方面，系统预设了超级管理员与普通运营员两类角色。超级管理员具备所有系统菜单和接口的完整访问权限，能够执行用户管理、角色分配、菜单编辑、系统参数配置等高危操作；普通运营员则仅被授予水果分类管理、商品管理和订单处理三个业务模块的操作权限，无法触及系统配置与用户管理模块，从而在权限粒度上实现了职责隔离与最小授权原则。水果分类管理功能支持对分类名、排序权重和图标的添加、修改、删除及查询。为维护数据唯一性与业务一致性，系统在分类创建和编辑时要求分类名称不可与已有的分类记录重复，若检测到同名分类则直接返回错误提示并阻止写入操作，排序权重字段仅接受正整数输入，用以控制前端展示顺序。商品管理模块支持水果品种的 CRUD 操作，并允许运营人员将水果图片上传至 MinIO 对象存储，自动生成静态访问 URL。在商品上架流程中，系统强制要求商品在设置为上架销售状态之前必须已经上传主图，否则接口将拒绝执行状态变更操作并提示运营人员补充主图信息，该规则旨在避免用户端出现无图商品的不良体验。此外，商品单价字段在后端被约束为不可为零或负数，规格描述字段长度上限为五百个字符以防止异常输入。订单处理工作流能够对全平台用户的订单流转进行监控，支持按待付款、已支付、已包装等条件进行过滤，并允许后台人员接单或处理退款。在订单状态流转的业务规则层面，系统严格限定状态只能单向递进，即从待付款流转至已支付，从已支付流转至已包装，从已包装流转至已完成，不允许逆向回退或跳级流转，任何试图违反该规则的操作请求都会在服务层被拦截并记录异常日志。

[工程图占位符: 订单状态流转图]
后台首页的运营大屏需要实时计算并展示当日营业额、累计订单量、库存报警数以及最新五条待处理包装订单，数据采用定时轮询与前端主动刷新相结合的方式更新。

在微信小程序端，用户的完整购买旅程从进入首页开始。首页加载时，小程序会请求后端接口获取水果分类列表和推荐商品数据，用户可以通过点击分类标签进入对应分类的商品列表页面进行浏览，也可以直接使用顶部搜索栏输入关键字进行模糊检索，搜索请求携带关键字参数发送至核心业务服务，后端在数据库层面执行商品名称的模糊匹配查询并返回结果列表。当用户对某件水果商品产生购买意向后，可以点击加入购物车按钮将其加入临时购物车，购物车中的每个条目记录了水果商品的唯一标识、选购数量和当时的单价，用户可以在购物车页面自由调整每件商品的购买数量或者将其移出购物车。进入结算流程后，用户首先需要选择或新增收货地址，地址簿管理功能支持多地址保存，每条地址记录包含收货人姓名、联系电话、省市区详细地址等字段，用户可以设定一个默认收货地址以简化后续操作。地址选择完成后，系统根据购物车中所有商品的单价与数量计算实付总金额，在结算确认页面向用户展示订单明细、商品小计和应付总额，用户确认无误后提交订单，此时临时购物车数据被转换为持久化的待付款订单记录写入数据库。最后在测试环境下，用户点击支付按钮调用模拟微信支付接口来闭环打通支付回调链路，模拟支付成功后订单状态自动更新为已支付。

[工程图占位符: U06-购物活动图]


在微服务间协作方面，当模拟支付成功后，系统需要驱动支付微服务 lgg-pay 跨模块触发核心业务微服务 lgg-business 中的订单数据库状态更新，并投递异步解耦消息来驱动通知微服务 lgg-notice 推送实时 WebSocket 包装警报。具体的数据流转路径为：支付微服务 lgg-pay 在确认支付模拟回调成功后，首先通过 OpenFeign 声明式客户端同步调用核心业务微服务 lgg-business 暴露的订单状态更新接口，将目标订单的状态从待付款修改为已支付并将支付完成时间写入数据库记录；紧接着，支付微服务向 RabbitMQ 消息队列投递一条包含订单编号和支付时间的事件消息，该消息被路由至预先绑定好的交换器和队列中；消息通知微服务 lgg-notice 作为该队列的消费者监听到消息到达后，解析消息体中的订单信息，构造格式化的订单提醒内容，并通过 WebSocket 长连接通道将包装提醒推送至管理后台的运营大屏，运营人员由此可以实时感知新到的已支付订单并及时安排包装发货。

3.2 非功能需求

在非功能性层面，系统从可用性、可维护性、安全性、性能以及可扩展性五个维度进行了全面的质量属性约束与验收标准设定。

在可用性维度上，系统必须保证本地单机运行环境下的演示稳定性。这要求前后台应用、各个微服务以及相关中间件能统一在 PM2 容器中托管，消除异常中断与端口残留隐患。每个微服务进程在 PM2 管理器中被配置为崩溃后自动重启模式，服务异常退出后 PM2 应当在不超过十秒的时间窗口内完成进程重新拉起并恢复对外服务能力，确保演示过程中不会因单个服务的偶发异常导致整体系统不可用。同时，前端管理后台页面应当在主流浏览器中正常渲染，不出现样式错乱或功能失效，微信小程序端应当在微信开发者工具与真机环境下均能正常加载和操作。

在可维护性维度上，服务的注册发现与配置管理要求完全动态化，由 Nacos 负责微服务实例的健康维护，使得 Gateway 网关无需在配置中显式硬编码服务物理 IP。每个微服务的核心配置项均从 Nacos 配置中心远程拉取，当需要调整数据库连接参数、Redis 地址或 RabbitMQ 凭证时，只需在 Nacos 控制台修改对应的配置文件并发布即可生效，无需重新编译或重新部署微服务的 JAR 包。各微服务之间的代码结构保持清晰的模块化边界，公共依赖统一由父工程 POM 管理版本号，避免依赖冲突和版本漂移，使得团队成员在并行开发不同微服务时互不干扰。

在安全性维度上，管理后台的所有 API 接口均受到 JWT 令牌鉴权保护，未携带有效令牌或令牌过期的请求将被安全过滤器拦截并返回 HTTP 401 状态码。系统对登录接口实施了防重放与防暴力破解机制，同一 IP 在短时间内连续登录失败超过五次后将被临时锁定。密码在存储层使用不可逆哈希算法加密，数据库中不存储明文密码。此外，网关层面配置了全局跨域安全策略，仅允许已知的前端域名来源发起跨域请求，防止 CSRF 攻击。

在性能维度上，各微服务的 Spring Boot 应用启动时间在本地开发环境下应当控制在不超过三十秒的范围内。后端 REST 接口在正常业务负载下的单次响应时间应当不超过五百毫秒，其中涉及数据库读写的核心接口应通过合理的索引设计和 Redis 缓存策略将响应时间控制在两百毫秒以内。水果分类列表作为高频读取且低频变动的数据，在首次从数据库加载后将被写入 Redis 缓存，后续的查询请求直接命中缓存返回，仅在分类数据发生增删改操作时才主动清除缓存并回源数据库重新加载。

在可扩展性维度上，所有核心微服务模块集成了 Spring Boot Actuator 指标，对外开放健康监测端点以展示服务的 UP 状态，这为未来接入 Prometheus 与 Grafana 监控体系奠定了数据采集基础。数据通信解耦和 RabbitMQ 消息投递具备高可靠性，通过自动创建并绑定 Exchange 与 Queue 来规避服务初始化抛错。系统在架构层面预留了水平扩展能力，当业务量增长时可通过 Nacos 注册多个同名服务实例实现负载均衡，Gateway 网关将自动感知新实例并在路由转发时采用轮询策略分配请求流量。

系统采用前后端分离与轻量微服务架构。用户通过管理端浏览器或微信小程序客户端发起 HTTP 请求，所有外部请求首先流经统一 API 网关 lgg-gateway。网关在接收到请求后，依次对请求路径执行断言匹配判定：网关配置中预定义了多组路由规则，每组规则包含一个路径断言和一个目标服务标识，当请求的 URI 路径前缀与某条断言规则相匹配时，网关即将该请求转发至对应的微服务实例。例如，路径前缀为 /admin 的请求被路由至后台管理服务 lgg-admin，前缀为 /business 的请求被路由至核心业务服务 lgg-business，前缀为 /pay 的请求被路由至模拟支付服务 lgg-pay，前缀为 /notice 的请求被路由至消息通知服务 lgg-notice。网关在转发过程中会自动通过 Nacos 服务发现机制将逻辑服务名解析为实际的服务实例地址和端口，从而实现动态路由而无需硬编码物理地址。

在跨域请求处理方面，由于管理后台前端运行在独立的端口上，浏览器发出的 API 请求属于跨域调用，网关通过全局跨域配置类 GlobalCorsConfiguration 对所有经过网关的请求统一添加 CORS 响应头，允许指定的前端域名发起跨域请求，并放行 OPTIONS 预检请求，从而在网关层面一次性解决了浏览器同源策略的限制，避免在每个微服务中重复配置跨域策略。针对微信小程序端的请求与管理后台浏览器请求的差异化路由策略，网关层面通过路径前缀进行自然区分：管理后台的请求主要集中在系统管理类接口，而小程序端的请求主要集中在业务查询和订单操作类接口，两类请求通过不同的路径断言被分发至不同的后端服务进行处理。

当请求到达目标微服务后，后端服务的控制器层接收请求参数并调用对应的服务层方法执行业务逻辑。在数据读取场景中，服务层首先检查 Redis 缓存中是否存在目标数据，若缓存命中则直接从 Redis 中读取数据构造响应对象返回；若缓存未命中，则调用持久层 Mapper 接口向 MySQL 数据库发起查询操作，将查询结果写入 Redis 缓存后再构造响应对象返回。在数据写入场景中，服务层完成业务校验后调用持久层接口将数据持久化至 MySQL 数据库，同时主动清除与该数据相关的 Redis 缓存条目以保证缓存与数据库的一致性。最终，响应对象沿原路经由网关返回给前端客户端，完成一次完整的请求响应链路闭环。各服务节点向 Nacos 注册中心发送心跳并进行服务注册，微服务间利用声明式的 OpenFeign 远程组件进行状态通信。数据库持久层采用 MySQL 实现，Redis 负责若依系统会话缓存与水果分类缓存，RabbitMQ 负责消息的异步发布订阅，MinIO 提供本地对象存储服务，WebSocket 保持长连接双向通道以推送订单提醒。

3.4 服务模块设计

[工程图占位符: U04-微服务模块依赖结构图]

系统的分布式后端在物理和逻辑上被拆分为五个核心微服务，各微服务在本地开发环境下分别监听独立的端口以避免冲突。在启动顺序上，系统遵循严格的依赖链路：首先启动 Nacos 注册中心与配置中心，确保后续各微服务能够正常拉取配置并完成服务注册；其次启动 Redis 缓存服务和 MySQL 数据库服务，为业务层提供数据存取基础设施；然后依次启动各后端微服务，包括 lgg-admin、lgg-business、lgg-pay 和 lgg-notice；待所有业务微服务注册完毕后再启动 lgg-gateway 网关服务，使网关能够通过 Nacos 发现全部可用的服务实例；最后启动前端管理后台应用，完成整体系统的初始化流程。

统一网关服务 lgg-gateway 监听 8090 端口，负责拦截全平台请求并执行动态路由解析，将特定前缀的 API 请求匹配转发给对应的微服务。该服务本身不承载任何业务逻辑，其核心职责在于路由转发、跨域处理和请求过滤。网关对外暴露的并非具体的业务接口，而是作为所有后端微服务接口的统一代理入口，对外仅展示 Actuator 健康监测端点。lgg-gateway 依赖 Nacos 提供的服务发现能力完成逻辑服务名到物理地址的动态映射，与所有下游微服务之间存在路由级别的依赖关系。

系统管理服务 lgg-admin 监听 8080 端口，负责若依系统的登录认证、安全过滤、菜单加载以及后台系统配置。该服务对外暴露的核心接口包括用户登录认证接口、获取用户信息接口、获取动态路由菜单接口、验证码生成接口以及系统参数配置管理接口等。lgg-admin 直接依赖 MySQL 数据库中的若依系统表完成用户和权限数据的读写，同时依赖 Redis 存储登录会话令牌和验证码信息，是整个后台管理系统的安全认证基座，不直接与其他业务微服务通信。

核心业务服务 lgg-business 监听 8088 端口，承载了水果分类、水果商品以及订单的持久化业务处理，是系统中业务逻辑最为密集的微服务。该服务对外暴露的核心接口涵盖水果分类的增删改查接口、水果商品的增删改查及图片上传接口、购物车管理接口、收货地址管理接口、订单创建与查询接口以及订单状态更新接口等。lgg-business 依赖 MySQL 数据库存取全部业务数据，依赖 Redis 缓存水果分类列表，依赖 MinIO 对象存储保存商品图片文件，同时对外暴露 Feign 接口供支付微服务 lgg-pay 跨服务调用以完成订单状态的同步更新。

模拟支付服务 lgg-pay 监听 8085 端口，专门处理微信模拟扣款逻辑。该服务对外暴露模拟支付下单接口和支付回调接口两个核心接口。在支付成功后，lgg-pay 通过 OpenFeign 客户端同步调用核心业务服务 lgg-business 暴露的订单状态扭转接口完成订单数据更新，并向 RabbitMQ 消息队列投递支付成功事件消息。因此，lgg-pay 同时依赖 lgg-business 的 Feign 接口和 RabbitMQ 消息中间件，是微服务间协作链路的发起节点。

消息通知服务 lgg-notice 监听 8086 端口，负责消费支付消息并通过 WebSocket 协议广播订单卡片提示。该服务对外暴露 WebSocket 连接端点，管理后台前端在页面加载时即与该端点建立长连接。lgg-notice 作为 RabbitMQ 消费者监听支付事件队列，在接收到消息后通过已建立的 WebSocket 通道将包装提醒实时推送至管理后台，是微服务间协作链路的末端节点，仅依赖 RabbitMQ 获取上游事件而不主动调用其他微服务接口。

3.5 数据库设计

系统在数据持久层设计上，为了兼顾大作业演示的低风险性与服务的逻辑拆分，采用在统一的 lgg_ruoyi 数据源下进行分表隔离的策略，预留了后续演进为多库多服务的架构空间。所有业务数据表与若依框架自带的系统表共存于同一个 MySQL 数据库实例中，业务表通过统一的命名前缀与系统表进行逻辑区分。数据库的初始化通过项目 sql 目录下的 lgg_ruoyi.sql 脚本完成，该脚本包含了数据库创建语句、全部表结构的 DDL 定义、索引创建语句以及必要的初始化数据插入语句，团队成员在本地搭建开发环境时只需导入该脚本即可获得完整的表结构与基础数据，极大地降低了环境配置的协作成本。

系统设计了水果分类表 lgg_category 以维护水果分类信息。该表包含自增主键 id 字段，数据类型为 bigint，作为分类记录的唯一标识；category_name 字段为 varchar 类型，长度限制为一百个字符，不允许空值，用于存储分类名称；sort 字段为 int 类型，默认值为零，用于控制前端展示时的排序权重；icon 字段为 varchar 类型，允许为空，用于存储分类图标的访问地址；create_time 和 update_time 字段均为 datetime 类型，分别记录分类创建时间和最近更新时间。在索引设计方面，category_name 字段上建立了唯一索引，确保系统中不会出现重名分类，该索引同时也加速了按分类名查询的检索效率。

水果商品表 lgg_fruit 存储水果商品的详细信息。该表包含自增主键 id 字段，数据类型为 bigint；fruit_name 字段为 varchar 类型，长度限制为二百个字符，不允许空值，用于存储水果商品名称；category_id 字段为 bigint 类型，不允许空值，作为指向水果分类表的外键引用，标识该商品所属的分类；price 字段为 decimal 类型，精度为十位整数两位小数，不允许空值，用于存储商品单价；image 字段为 varchar 类型，长度限制为五百个字符，允许为空，用于存储商品主图在 MinIO 对象存储中的访问 URL；status 字段为 tinyint 类型，默认值为零表示下架状态，值为一表示上架销售状态；description 字段为 varchar 类型，长度限制为五百个字符，允许为空，用于存储商品的规格描述信息；create_time 和 update_time 字段记录时间戳。在索引设计方面，fruit_name 字段上建立了全文索引以支持商品名称的模糊检索功能，category_id 字段上建立了普通索引以加速按分类查询商品列表的操作。

订单表 lgg_order 作为核心表承载了全部订单数据。该表包含自增主键 id 字段，数据类型为 bigint；order_no 字段为 varchar 类型，长度限制为六十四个字符，不允许空值，用于存储系统生成的唯一业务订单号；status 字段为 tinyint 类型，不允许空值，用于标识订单当前所处的流转状态，其中值零代表待付款、值一代表已支付、值二代表已包装、值三代表已完成；user_id 字段为 bigint 类型，不允许空值，作为购买用户的标识外键；total_amount 字段为 decimal 类型，精度为十位整数两位小数，不允许空值，用于存储订单的实付总金额；address 字段为 varchar 类型，用于存储用户提交的收货地址全文；pay_time 字段为 datetime 类型，允许为空，在支付完成后由支付回调写入具体的付款完成时间；create_time 和 update_time 字段记录时间戳。在索引设计方面，order_no 字段上建立了唯一索引以保证订单号在全局范围内的唯一性，该索引同时也是支付回调时按订单号检索目标订单的主要查询路径；status 字段和 user_id 字段上分别建立了普通索引以支持按订单状态过滤和按用户查询订单的高频业务场景。

订单明细表 lgg_order_detail 则通过外键与订单表以及水果商品表相连，用于多对多映射记录具体订单下的水果名称、单价、购买数量以及子项总额。该表包含自增主键 id 字段；order_id 字段为 bigint 类型，不允许空值，作为指向订单表的外键引用；fruit_id 字段为 bigint 类型，不允许空值，作为指向水果商品表的外键引用；fruit_name 字段为 varchar 类型，用于冗余存储下单时刻的水果名称以防止商品改名后影响历史订单展示；price 字段为 decimal 类型，用于冗余记录下单时刻的商品单价；quantity 字段为 int 类型，不允许空值，记录该商品的购买数量；subtotal 字段为 decimal 类型，不允许空值，记录该明细项的金额小计。order_id 字段上建立了普通索引以加速按订单号查询明细列表的操作。

在外键约束策略方面，本系统在物理层面未强制启用数据库级别的外键约束，而是在应用层通过业务代码逻辑保证引用完整性。这一设计选择基于两方面考量：其一，在微服务架构向多库演进的过程中，跨库外键约束在物理上不可实现，提前在应用层管理引用关系有助于平滑过渡；其二，去除物理外键可以降低数据库在高并发写入时的锁竞争开销，提升批量插入和更新操作的吞吐量。

关于数据库分表隔离策略与未来多库演进路径，当前阶段所有业务表与系统表共享同一个数据库实例，这在课程设计演示环境下极大地简化了部署复杂度和运维成本。然而，系统在设计之初便充分考虑了未来业务规模增长后的架构演进需求。各微服务在代码层面仅访问与自身业务职责相关的数据表，不存在跨服务直接访问其他服务所属数据表的情况，这意味着当系统需要演进为多库架构时，只需为每个微服务分配独立的数据库实例，将其所属的业务表迁移至对应的数据库中，并修改各微服务的数据源配置指向新的数据库地址即可完成拆分，业务代码层面无需进行任何改动，从而实现了从单库分表到多库多服务的低成本平滑迁移。
