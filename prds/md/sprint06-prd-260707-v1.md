# Sprint 06 PRD: 真实微信用户绑定、持久化数据同步与答辩级数据流闭环

Last Updated: 2026-07-07 00:00

## 大目标

下一阶段从“功能可演示”推进到“数据真实、链路可解释、重启可恢复、答辩可追问”。本 Sprint 以真实微信小程序登录、用户 token 与 openid 绑定、MySQL 持久化、管理端首页 ECharts 读取真实业务数据、以及 Playwright/Python 测试注入为核心，建立前端、小程序、后端、数据库、可视化大屏之间的一致数据闭环。

---

## 当前真实状态（2026-07-07）

| 模块 | 当前状态 | 风险 |
|------|----------|------|
| 微信登录 | 后端已有 `jscode2session` 调用，但配置仍是 mock appid/secret，openid 为空时降级为 `mock_openid_{code}` | 每次重新加载可能形成临时用户或丢失 token 上下文 |
| 小程序 token | 主要存在 Vuex 内存态，未形成可靠本地持久化恢复 | 重启小程序或重新编译后需要重新登录，页面看起来“没数据” |
| MySQL 持久化 | `lgg_user`、地址、购物车、订单表具备落库能力 | 需要确认每条链路是否都通过真实 userId/openid 写入 |
| 管理端首页 | 营业额/订单统计依赖后端统计接口，且只统计已完成订单 | 用户刚支付或待配送订单不会立即进入营业额，容易被问“为什么不同步” |
| 测试注入 | 已有真实用户下单测试草案 | 需要用 Playwright 或 Python+uv 固化可重复数据集 |
| 小程序返回 | 订单详情页左上角已增加页面栈判断和历史订单/首页兜底 | 页面栈为空时不再表现为点击无反应 |

## 关键阶段与里程碑

### Phase 1: 小程序导航与登录状态止血
- **M1.1** 订单详情页 `goBack()` 增加页面栈判断和历史订单兜底。
- **M1.2** 梳理所有从支付成功页、历史订单页、消息入口进入详情页的导航方式。
- **M1.3** 小程序 token 写入本地存储，启动时恢复 Vuex token 和 userInfo。
- **M1.4** request 拦截器在 token 缺失时触发静默登录或引导重新登录。

**验收标准：** 订单详情页左上角返回在有上级页面时回上一页；无页面栈时进入历史订单或首页。小程序重启后仍能带 token 查询用户历史数据。

---

### Phase 2: 真实微信登录绑定与 MySQL 用户持久化
- **M2.1** 调研并配置微信开发者平台 appid/secret，区分 dev/test/prod。
- **M2.2** 后端 `wx.login code -> jscode2session -> openid/session_key` 流程可观测，失败时明确降级原因。
- **M2.3** `lgg_user.openid` 建唯一索引，同一 openid 登录执行查询或更新，不重复造用户。
- **M2.4** 登录成功签发业务 token，token payload 绑定 userId，所有用户接口从 token 解析当前用户。

**验收标准：** 同一微信账号连续登录三次，数据库只有一条用户记录；地址、购物车、订单均绑定同一个 userId。

---

### Phase 3: 管理端首页真实数据与 ECharts 同步
- **M3.1** 统一定义营业额口径：默认只统计已完成且已支付订单，另提供待配送/待接单运营指标。
- **M3.2** Mapper 层新增真实聚合 SQL：营业额、有效订单、商品销量 TopN、近 7 日订单趋势。
- **M3.3** Service 层将 SQL 结果封装为 VO，Controller 返回管理端首页。
- **M3.4** ECharts 图表读取接口数据，移除静态 mock。

**验收标准：** MySQL 插入或测试脚本生成的订单完成后，管理端首页 ECharts 和指标卡能实时反映聚合结果。

---

### Phase 4: 真实用户订单数据注入与覆盖测试
- **M4.1** 在 `tests/` 内维护 3-5 个真实用户样本：姓名、电话、地址、商品、金额、状态。
- **M4.2** 使用 uv 建立 Python 测试环境，优先通过接口注入数据，必要时用 Playwright 驱动前端。
- **M4.3** 覆盖登录恢复、下单、支付、完成、统计同步、订单详情返回。
- **M4.4** 输出测试报告，标明哪些数据写入 MySQL、哪些数据只在前端内存或缓存中。

**验收标准：** 测试数据能重复注入和清理；关键业务条件覆盖通过；重启服务后持久化数据仍存在。

---

### Phase 5: 答辩材料同步与追问防御
- **M5.1** 更新 `issue.md`：数据项存储表、接口路径、SQL、DTO/VO、Controller、前端组件。
- **M5.2** 写清两个典型流程：微信登录恢复、用户下单到管理端 ECharts。
- **M5.3** 增加“老师追问判断框架”：先定位数据来源，再定位 SQL，再定位封装层，再定位页面渲染。

**验收标准：** 面对“这个字段在哪里存、用什么 SQL 查、怎么传到页面、为什么营业额不同步”等追问，能给出确定答案和文件级定位。

---

## 范围边界

- 本轮接入真实微信登录的目标是“真实 openid 绑定业务用户”，不要求上线真实微信支付。
- 管理端首页统计按 MySQL 已完成订单口径实现，待支付、待接单、配送中订单进入运营指标而非营业额。
- 测试数据优先走 API 和 Playwright 注入，避免直接手工改库造成业务链路不可解释。
- 继续保留 mock 登录/支付作为本地无微信凭证时的开发降级，但必须在文档和日志中明确标记。
