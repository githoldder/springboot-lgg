### 本轮必须处理的高危问题

| 编号 | 风险 | 影响 | 优先级 |
|------|------|------|--------|
| SEC-A | 下单金额信任前端传参，存在抓包改价风险 | 真实支付接入后可造成低价支付、账单亏损 | P0 |

| SEC-D | 支付/下单链路无库存扣减与并发保护 | 高并发下会超卖，导致履约和账务不一致 | P0 |
| OPS-A | 催单接口缺少 Redis 限流和状态判定 | WebSocket 消息爆炸，后台运营被高频干扰 | P1 |
| OPS-B | 订单缺少预计送达与超时标记 | 后台无法区分紧急订单，履约风险不可见 | P1 |
| OPS-C | 未支付订单缺少自动关单与退库机制 | 长期挂起订单占库存，影响真实库存可售量 | P1 |

## 关键阶段与里程碑

### Phase 1: P0 安全止血（金额防篡改 + 平行越权）
- **M1.1** `OrderServiceImpl.submitOrder()` 强制使用后端购物车实算金额覆盖 `OrdersSubmitDTO.amount`。
- **M1.2** `userCancelById(Long id)` 增加订单归属权校验，仅允许订单所属用户取消自己的订单。
- **M1.3** `repetition(Long id)` 增加订单归属权校验，防止读取他人订单明细。
- **M1.4** 为金额篡改、越权取消、越权再来一单补充接口级回归测试。

**验收标准：** 抓包传入 `amount=0.01` 后，数据库订单金额仍等于购物车实算金额；用户 A 调用用户 B 的取消/再来一单接口时返回业务异常，且数据库状态和购物车均不被篡改。

---

### Phase 2: 库存一致性与并发防超卖
- **M2.1** 梳理 `lgg_fruit` 库存字段及当前库存数据来源，确认是否已有 `stock` 字段或需要新增迁移。
- **M2.2** 支付成功或订单确认节点执行库存扣减，采用 SQL 条件扣减：`stock >= buy_num`。
- **M2.3** 批量扣减时校验影响行数，任一商品库存不足则阻断状态流转并记录补偿任务。
- **M2.4** 取消订单、支付超时关单、退款成功后执行库存回滚。
- **M2.5** 为并发扣减补充压测/并发测试，验证不会出现负库存。

**验收标准：** 多线程同时购买同一库存商品时，成功订单数不超过库存；库存不足订单不会进入已支付/待接单状态；取消或退款后库存可正确回补。

---

### Phase 3: 催单防刷与状态化提醒
- **M3.1** 在 `reminder(Long id)` 中加入 Redis 原子限流锁：`lgg:order:reminder:lock:{orderId}`，TTL 60 秒，`NX` 写入。
- **M3.2** 催单前校验订单状态，仅允许待包装/待派送/配送中等可催单状态触发提醒。
- **M3.3** 对已完成、已取消、待支付订单返回明确业务提示，不发送 WebSocket。
- **M3.4** 小程序端催单按钮增加 60 秒倒计时置灰，降低无效请求量。
- **M3.5** 管理端区分普通来单提醒与催单提醒，避免误导仓库重复打包。

**验收标准：** 同一订单 60 秒内重复催单只触发一次 WebSocket；禁用状态订单不会发送提醒；前端按钮倒计时和后端限流结果一致。

---

### Phase 4: 配送时效、超时高亮与后台可观测
- **M4.1** 在 `lgg_orders` 增加 `estimated_delivery_time`、`overtime_status`、`actual_delivery_time` 字段及迁移脚本。
- **M4.2** 下单时默认写入预计送达时间：下单时间 + 30 分钟，后续支持用户选择配送时间。
- **M4.3** 管理端订单列表查询时动态计算超时状态：当前时间超过预计送达且订单未完结则置为超时。
- **M4.4** 管理端订单列表和详情页对超时订单红色高亮，并播放独立预警提示音。
- **M4.5** 订单完成时写入 `actual_delivery_time`，用于后续履约分析。

**验收标准：** 构造一条预计送达时间早于当前时间且未完成的订单，管理端列表显示超时标记和高亮；完成订单后不再显示超时。

---

### Phase 5: 自动关单、退库与补偿通道
- **M5.1** 选型 RabbitMQ 延迟队列或 Redis Key 过期监听，实现未支付订单 15 分钟自动取消。
- **M5.2** 自动关单逻辑必须复用统一取消服务，确保状态校验、库存回滚、日志记录一致。
- **M5.3** 配送超过 24 小时未确认完成时生成运营预警，不直接强制完成订单。
- **M5.4** 退款失败时写入人工补偿记录，保留订单号、支付单号、失败原因和处理状态。
- **M5.5** 补充异常流转日志，支持后续按订单号追踪关单、退库、退款和人工补偿状态。

**验收标准：** 未支付订单 15 分钟后自动变为已取消并回补库存；超过 24 小时配送中订单产生预警；退款失败不会静默丢失，后台可查询补偿记录。

---

### Phase 6: 回归测试与验收演示
- **M6.1** 编写 API 测试用例覆盖：金额篡改、越权取消、越权再来一单、重复催单、自动关单。
- **M6.2** 编写并发测试覆盖：库存扣减、双管理员指派骑手、重复支付回调幂等。
- **M6.3** 编写 E2E 演示脚本覆盖：下单 → 支付 → 催单 → 超时高亮 → 完成/取消。
- **M6.4** 更新 `issue.md` 的执行状态，把设计项标注为已落地/待验证/阻塞。

**验收标准：** P0/P1 场景测试全部通过；演示链路能稳定复现业务防御效果；文档状态与代码真实状态一致。

## 范围边界

- 本轮优先处理订单域：`OrderServiceImpl`、订单 Mapper、订单 DTO/VO、订单数据库迁移、管理端订单列表、小程序催单入口。
- 真实微信支付仍可继续使用 mock 支付演示，但回调幂等、金额一致性和补偿设计必须按真实支付标准实现。
- 不在本轮重构完整骑手系统，只实现指派并发保护与配送超时预警。
- 不把 WebSocket 离线消息做成持久化 IM 系统，管理员离线后的兜底仍依赖订单列表条件查询。
